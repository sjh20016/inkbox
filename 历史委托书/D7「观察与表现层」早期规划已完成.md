# D7「观察与表现层基建」

核心目标不是继续扩世界，而是把已经存在的模拟深度转换成玩家真正能感知的东西。

这一阶段完成后，《坐天观井》应该从：

> “后台发生很多事，右栏告诉我发生了什么”

推进到：

> “我能看到事情发生，镜头会回应，我能记挂某个人，并沿着他的关系与命运一路追下去。”

同时，D7 还负责把当前几个“已知红”和明显工程裂缝清掉，给后续 D8 视界深化铺一块干净地基。

我建议拆成 **A～G 七个工程包**。严格按顺序施工，一个包完成、测试、提交后再进入下一包。不要让模型一次横跨多个包。

1. **D7-A：Baseline Zero，先把工程基线清零。**

   这一包禁止新增任何玩法。目标只有一个：让当前主线从“功能正常但允许几个已知红”进入“任何红灯都代表新问题”。

   先处理 `intervention` 的 chronicle kind。当前 `main.js` 会执行 `world.record(..., 'intervention')`，但 `KIND_TAG` 没有完整登记。不要新建一套“干预面板”，直接确定它在现有分类体系里的归属。如果它本质是天道行为记录，我倾向归入现有 world 类或现有最接近的分类。同步处理 `KIND_TAG`、必要白名单以及 smoke 的静态扫描规则。

   处理 `worldEventState` 与存档键 `worldEvents` 的契约问题。这里不要为了让测试绿而直接粗暴改存档键，因为旧档已经使用 `worldEvents`。推荐保留外部存档字段 `worldEvents`，内部继续允许叫 `worldEventState`，但在 save-equivalence 中把它明确登记成一个“有意的字段映射”。后续 D7-G 再考虑 schema 单源化。验收标准是 save-equivalence 不再把这组合法映射判成红。

   修幽冥 `decayYears < 0` 的永久存在语义。禁止继续使用 `-1e9` 表示永不消散，因为现有判断是 `day >= ghostDecayDay`。推荐定义独立常量，例如 `NEVER_DECAY_DAY`，采用可安全 JSON 往返的巨大正有限值。不要直接用 `Infinity`，避免 JSON 序列化成 `null` 一类边缘行为。新增测试：普通正寿命会按时消散，负寿命不会在至少数万年模拟内被消散，存读档后语义保持。

   修 browser playtest 中人物面板点击竞态。不要继续使用“失败就重跑”的纪律。优先改为稳定 DOM 触发，或者在取坐标和点击前等待一次稳定帧。还要补一条反向测试：关闭人物卡后必须同时验证可见状态与目标 ID，而不能因为旧 `textContent` 残留误判成功。

   处理 build 的 tar 路径问题。推荐让 `inkbox-package.mjs` 使用相对输出路径配 `cwd`，避免 Windows 盘符被 GNU tar 解释成远程主机。不要针对某一种 tar 加一个只在另一种 tar 上失败的参数。打包逻辑只负责产物，不应该依赖“System32 恰好排在 PATH 前面”。

   同步清理文档状态漂移。至少修：
   - `BACKLOG.md` 中仍写“夺舍未开工”的旧描述。
   - `PLAYER_GUIDE.md` 的观察工具补上幽冥视界。
   - `版权说明.md` 的旧版本号。
   - `README / STATUS / THREE_REALMS / PLAYER_GUIDE` 的当前阶段统一为 D7 前置完成状态。
   - 不在这一包大规模重写 `STATUS.md`，只修事实错误。

   A 包验收必须是：`npm test`、`test:regression`、`test:three-realms`、`test:save-equivalence`、`test:simulation` 全部没有“允许存在的红”；browser playtest 连续多跑几次不能靠偶然变绿；build 在普通 Windows cmd/PowerShell 与 Git Bash PATH 环境至少不再因为盘符解析失败。

   A 包完成以后打一个单独 commit。建议提交名类似：

   `fix: establish zero-red D7 baseline`

2. **D7-B：建立“表现事件”基础设施，这是整个阶段最重要的架构包。**

   这一包仍然不做具体华丽特效。只建事件通道。

   不建议直接在 `Sandbox` 里到处写：

   `this.fx.push(...)`

   因为那很快会重新变成一个新的巨型耦合点。

   建议建立一个很薄的“运行时事件层”。它的职责是：

   模拟发生了一件事  
   → 产生一个不影响模拟结果的 transient event  
   → UI/Camera/FX 可以消费  
   → 不进存档  
   → 不参与随机流  
   → 消费完立即丢弃。

   推荐增加一个类似：

   `src/inkbox/core/runtimeEvents.js`

   或：

   `src/inkbox/world/runtimeEvents.js`

   不要放进 `render/`，因为模拟模块不能反向依赖渲染模块。

   建议 API 只有少数几个：

   ```js
   emitRuntimeEvent(world, type, payload)
   drainRuntimeEvents(world)
   peekRuntimeEvents(world)
   ```

   事件对象统一形状，例如：

   ```js
   {
     type,
     plane,
     day,
     x,
     y,
     subjectId,
     targetId,
     intensity,
     data
   }
   ```

   字段全部可选，但 `type / plane / day` 尽量统一。

   禁止把 `performance.now()`、DOM 节点、Canvas 对象塞进模拟事件。模拟层只描述“发生了什么”；表现层收到以后再给事件赋真实时间。

   第一版类型不要贪多。只定义真正值得演出的核心事件，例如：

   - `tool-impact`
   - `tribulation`
   - `ascension`
   - `rift-open`
   - `rift-cross`
   - `possession`
   - `war-start`
   - `sect-fall`
   - `major-death`

   但 B 包本身只需要把协议定好，不要求全部接入。

   事件队列必须有上限，比如 256 或 512。若高速模拟瞬间产生大量事件，不允许无限增长。超出时优先丢最老的表现事件，因为它们只是视觉反馈，不是历史真相。

   `runtimeEvents` 明确是 transient state：
   - 不写 save。
   - 不参与 save-equivalence。
   - 读档后为空。
   - 上界、凡间、幽冥可以分别产生。
   - drain 不允许改 simulation state。

   给它写一个非常小的 Node 测试，验证：
   - emit 顺序。
   - drain 后清空。
   - 队列封顶。
   - plane 不串。
   - 调用事件系统不会消费任何 RNG。
   - serialize 前后不存在这个字段。

   这一包最重要的一条纪律：

   **表现事件不是第二份编年史。**

   `world.record()` 负责历史。

   runtime event 只负责“此刻闪一下”。

   不允许两个系统互相替代。

3. **D7-C：相机 2.0，让“找到某人”从瞬移变成真正的镜头行为。**

   当前 `Camera` 保留 `x / y / zoom` 的直接操作，不要重写成永久追踪型相机。

   新增一次性镜头动作系统，例如：

   ```js
   camera.focusOn(x, y, {
     zoom,
     duration,
     hold
   })
   ```

   Camera 内部可以维护：

   ```text
   transition.active
   fromX/fromY/fromZoom
   toX/toY/toZoom
   elapsed
   duration
   ```

   每帧执行：

   `camera.update(dt)`

   使用 ease-out 或指数缓动都可以，但必须在固定时长内准确结束，不能无限趋近。

   推荐默认体验：
   - 找人物：0.6～0.9 秒。
   - 找宗门：0.7～1.0 秒。
   - 大事件自动聚焦若以后启用，可以稍慢。
   - 不要做镜头晃动。
   - 不要自动跟随人物移动。

   最重要的是“玩家输入立即接管”：

   玩家只要开始右键拖动、滚轮缩放、按 H 回全图，立刻取消当前 tween。

   所以不要让相机变成黏糊糊的追踪器。

   把目前 `main.js` 中至少两类直接赋值：

   ```js
   camera.x = ...
   camera.y = ...
   camera.zoom = ...
   ```

   改成 `focusOn()`。

   `fit()` 默认仍保留立即生效。可以额外做 `focusFit()`，但不要强制把所有 fit 都动画化。

   另外加一个“落点反馈”。镜头移到人物/宗门之后，目标位置出现一个大约 1.2 秒的收缩墨环。这个墨环属于表现层，不属于 Camera 本身。

   C 包测试至少覆盖：
   - focus 最终能准确落到目标。
   - 中途用户 pan 会取消。
   - zoomAt 会取消。
   - clamp 仍然有效。
   - 没有 transition 时行为与旧 Camera 一致。
   - 高倍速不会改变镜头动画真实时长，因为镜头走 real-time，不走 game day。

4. **D7-D：FX Layer 1.0，让已有大事件第一次真正“发生在画面上”。**

   新建独立文件：

   `src/inkbox/render/fxLayer.js`

   不要塞进已经比较大的 `unitsLayer.js`。

   FX Layer 读取 B 包的 runtime events，把事件转换成短命 render effect。

   FX 内部使用 real-time：

   ```text
   bornAt
   duration
   elapsed
   ```

   不使用 `world.day` 作为动画时间。

   第一批只做 6 类，足够了：

   **雷霆 / 渡劫**

   落点上方到目标之间画一条快速折线，100～200ms 强亮，随后 300～500ms 淡出。可以加一圈非常轻的地面扩散线。不要做屏幕闪白。

   **陨石**

   先给一个高速落点轨迹，再出现冲击圆与几条放射状墨裂纹。总时长控制在 0.8～1.2 秒。

   **飞升**

   不做西式光柱。更适合 Inkbox 的方式是人物位置出现向上的淡墨粒子或青白墨点，逐渐拉散，持续约 1.2 秒。

   **裂隙开启**

   根据裂隙区域或中心位置画一条短暂开裂的墨线。注意真正的裂隙实体已经有自己的世界表现，这个 FX 只是“刚开出来的那一下”。

   **夺舍 / 附身**

   不要做夸张鬼脸。人物周围一圈冷墨向内收拢，再短暂出现双重轮廓即可。

   **战争开始**

   先只做两宗势力据点之间一条短暂裂纹/墨线。不要常驻，常驻战争显示留给 F 包。

   FX 绝对不能调用 `Life.rng`、`rift rng`、`upper rng`。

   如果需要随机折线，可以从：

   `event.day + event.x + event.y + subjectId`

   派生视觉哈希，或者使用 render 自己的 local random。

   最好使用确定性视觉哈希，这样 browser screenshot 更稳定。

   做性能保护：
   - 同时活跃 FX 设置上限。
   - 超上限优先丢低优先级效果。
   - 不生成大量 DOM。
   - 全部 Canvas 绘制。
   - 暂停世界时 FX 仍应继续播完，因为这是显示动画，不是模拟时间。
   - 游戏开到“飞”速时也不能让动画缩成 1 帧。

   然后逐步把已有事件接进 B 包，不允许为了 FX 修改模拟判定结果。

   验收原则：

   **删掉整个 fxLayer.js，游戏模拟结果应该逐字不变。**

5. **D7-E：“记挂”系统 1.0，这是本阶段最重要的玩法包。**

   不叫“收藏”，我更建议叫：

   **记挂**

   它符合天道观察众生的语感。

   目标不是做任务追踪器，而是允许玩家说：

   > “这个人，我想继续看。”

   在人物检视卡增加一个按钮：

   `☆ 记挂此人`

   记挂后变成：

   `★ 已记挂`

   不建议直接把它放到 `world.entities` 上，因为这是玩家观察状态，不属于世界规律。

   更合理的是把它存到存档 meta 或一个专门的 observer state 中。

   数据形状第一版尽量小：

   ```js
   {
     key,
     name,
     addedDay,
     lastKnownPlane,
     lastKnownId
   }
   ```

   总数限制，例如 12 或 16 人。不要无限。

   关键问题必须在工程开始前定死：

   **记挂的是“这一世的人”，不是灵魂。**

   所以第一版规则：

   - 活着时正常跟踪。
   - 死亡以后仍保留在“记挂”列表，状态变成“故人”，点击打开史册。
   - 飞升以后若已有可靠的跨界来历引用，显示“已入上界”，点击定位或打开上界记录。
   - 若没有足够可靠的跨界 identity，不允许靠名字猜。
   - 转世后不自动继承记挂。
   - 夺舍后记挂仍指向这具人生记录，但状态必须显示“异魂占身”或等价提示。
   - 不自动暂停游戏。
   - 不弹模态框。
   - 不因为记挂给角色任何数值 buff。
   - 不影响 AI 行为。

   UI 最好不要再新增一个巨大的右栏一级区域。

   可以把“记挂”放进“值得关注”下面，成为一个折叠子区：

   ```text
   值得关注

   天道记挂 · 3
   ★ 张三   金丹 · 在世
   ★ 李四   已飞升上界
   ★ 王五   故于仙历 312 年
   ```

   点在世人物：
   - 镜头走 C 包的 focus。
   - 打开人物卡。
   - 出一个收缩墨环。

   点故人：
   - 打开对应逝者传记。
   - 不移动到一个已经不存在的人身上。

   玩家记挂的人发生重大事件时，可以在“记挂”标题上出现一个很轻的红点，但不要一开始就造复杂通知中心。

   所谓重大事件第一版只认已有编年史 kind 中最重要的几类：
   - 大境界突破。
   - 入宗/立宗。
   - 大战。
   - 渡劫。
   - 飞升。
   - 夺舍。
   - 死亡。

   实现时最好复用 `world.record(..., actors)` 中已有的 actors，而不是通过解析文字判断“张三是不是出现在句子里”。

   要补测试：
   - 记挂列表存读档。
   - 上限。
   - 取消记挂。
   - 人死亡后不会丢失。
   - 人不存在时不会抛错。
   - 同一个人不能重复加入。
   - 读老档时为空。
   - 记挂状态不进入三界人口守恒。
   - 记挂不会改变 RNG。

6. **D7-F：关系与战争可视化，把已经存在的社会戏剧从文字里挖出来。**

   这一包严格禁止修改 `relations.js` 和 `war.js` 的核心判定。

   第一部分是人物局部关系图。

   不做全世界社会网络。

   只做“当前选中人物的一跳关系”。

   人物卡增加：

   `查看关系`

   展开一个小型 Canvas 或 SVG。

   中心是当前人物。

   周围最多显示 8～12 个有直接关系的人。

   优先级可以按：
   - 道侣
   - 师父
   - 弟子
   - 宿敌/仇怨
   - 亲缘
   - 同袍/同道
   - 旧师徒

   关系太多时按 score 绝对值和关系类型优先级裁剪。

   不要用巨大彩虹色。

   可以主要依赖：
   - 线型。
   - 线粗。
   - 少量色差。
   - 标签。

   比如：
   - 师徒：实线。
   - 道侣：双线或更柔的线。
   - 宿敌：断裂线。
   - 仇怨：锯齿。
   - 已死亡关系：淡线。

   点击外圈人物：
   - 活着 → 打开他的检视卡并 focus。
   - 已进入史册且能找到 → 打开史册人物。
   - 查不到 → 显示“此人已不可考”，不要抛错。

   第二部分是战争可见化。

   不需要增加战争玩法。

   只需要回答：

   > “现在地图哪儿正在打？”

   从现有战争状态和势力据点读取双方位置。

   第一版建议只在：
   - 当前观察某个宗门；
   - 或打开“战争显示”；
   - 或战争刚开始后的几秒；

   显示战线。

   不建议默认永远把所有战争线画在地图上，否则几十个势力时会变成蜘蛛网。

   表现可以是一条不断轻微断裂、呼吸的墨线，不必加图标。

   战争结束后常驻线立即消失。

   这里非常适合新建：

   `render/overlayLayer.js`

   让它负责：
   - 记挂目标环。
   - 活跃战争线。
   - 未来视界辅助标记。

   不要继续扩 `unitsLayer.js`。

### 整个 D7 阶段的硬性禁止事项

这一阶段请你在所有模型委托书最前面钉死这些规则。

**禁止新增三界生态。**

所以不做：
鬼城、鬼宗、仙官体系、邪祟种族、上界政治、跨界战争、第四世界。

**禁止修改数值平衡。**

没有强理由不要动：
出生率、突破率、战争概率、裂隙概率、鬼魂概率、寿元。

**禁止为了演出消费 simulation RNG。**

表现层视觉随机必须独立。

**禁止大规模重写 main.js。**

D7 可以把新东西放进新模块，并顺手把少量相关代码移出去，但不要发起“重构整个 Sandbox”工程。

**禁止重写存档格式。**

D7 只允许添加观察层需要的最小兼容字段。实体 row 数组整体迁移放以后专门阶段。

**禁止引入 React/Vue/Vite/Three.js。**

当前零依赖架构继续保持。

**禁止做随机轶事生成器。**

D7 的目标是让真实模拟事件更可见，而不是往编年史里灌更多没有状态基础的文学噪声。

**禁止音频。**

我建议音频等 D7 完成后作为 D8 的独立小包。原因很简单，先把“事件从哪里来、谁消费”这根管线修好，音频以后只需要成为 Presentation Event 的另一个消费者。

A 包和 B 包最需要谨慎。

优先交给 **GPT-6 Luna Max** 做一次架构审查和实施，或者 Luna 先设计、DeepSeek 执行，再让 Luna review。

因为 A 会碰存档契约，B 会决定以后整个表现层的依赖方向。

C 和 D 很适合 **DeepSeek V4.1**。

### D7 完成以后，玩家体验应该出现这些明确变化

进入世界之后，你点“值得关注”的人物，不再啪一下瞬移，而是镜头自然滑过去，人物位置有一道很短的墨环。

某个人渡劫，地图上真的能看到雷落下来。

有人飞升，能看到那个人从地图上的位置被一缕墨气带走。

玩家看到一个有趣的人，可以点“记挂”。

五百年以后他死了，记挂名单不会凭空消失，而会告诉玩家：

> “仙历 527 年，已故。”

点击进去，就是他的整个人生。

点他的关系，可以看到他的师父、道侣、徒弟、宿敌。

两宗正在打仗，不用翻编年史才能知道，地图本身会留下轻微战争痕迹。

而所有这一切都不应该改变：

**同样种子、同样玩家操作下，原本世界会发生什么。**

这一句就是 D7 最核心的验收标准。

如果完成 D7 后重新跑同种子长测，模拟结果因为“加了特效”发生明显漂移，那这一阶段就是失败的。

D7 做完之后，再进入 D8「视界 2.0」就会顺得多。因为届时裂隙、跌入幽冥、鬼爬出、物品泄漏、夺舍、飞升都已经有统一的 Presentation Event 管线，视界只需要把这些事件变成“透过世界表面看见另一边发生的事”，而不是重新造第三套反馈系统。

这会是我目前最推荐的下一阶段路线。
