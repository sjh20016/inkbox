# WX-S1 性能与保存边界

运行 `npm run profile:wanxiang:s1:perf`，输出 `reports/local/wx-s1/perf/acceptance.json`，包含实际 HEAD、源码文件哈希、CPU/Node、原检查点哈希、单人物100次查询延迟及四次原生续跑摘要。准确测量结果以该文件和最终 PR 为准。

## 成本合同

本包没有正式事实事件监听器，也没有模拟或渲染调度接线。每原生推进步骤故事检查/候选/入选均为 0，每事件增加的处理与分配为 0，每 rAF 故事编译为 0；这些是源码接线边界与专项静态检查的结果，不是通过采样推断的平均值。`Life.step` / `stepEntity` / `advanceWorld` / `readEffects` 源码未修改。正式 UI 的读取按钮才会进入候选匹配；HUD 只重绘已读快照或重新挂回同对象 DOM。

单人物查询至多读取该 Profile 的 24 正式经历、128 命途回执和三件原物履历；有证回助查询只检查稳定引用的对象，不按姓名 join 全人口。当前原物唯一归属核验会在主动查询时检查三界库存，不能从这个线性成本宣称无限人口下常数时间。全局 `readWorldStories` 仅用于主动研究/导出，不进入产品刷新。

候选经稳定排序、去重、360 日同模板冷却及每人一个主钩子筛选，世界读侧最多 24 开放/96 已结，单卡来源与节点有界。无来源时空白，不为了填配额生成事件。沉寂历史不参加高频匹配。

## 同一成熟检查点的比较

脚本使用真实 100 年与从同一检查点恢复续跑的 400 年世界。预热后测100次单人物命簿提取，记录中位/P95/最大延迟；独立恢复四次并按 A/B/B/A 顺序各推进30日，A关闭观察读取，B每3日推进后主动读取同一人。各次都计算 `serializeWorld` 加 `captureRuntimeState` 的完整摘要，涵盖正式人物/地点/宗门、原物及归属、资源、Life 与登记随机流。

每轮先深克隆检查点输入，和 WX-D 既有成熟回放脚本一致；原生读档会保留若干冷史/宗门资源引用，复用同一个输入对象会串扰后续试验。专项还验证推进后原输入逐字不变，未放宽等价断言。

同时分开报告 Life.step 墙钟和显式读取时间。读取发生在 Life 之后，Life 的墙钟抖动不能单凭包含时间归因于故事；没有伪造故事开关改变人物出生、事件或签序。查询后的堆差是 GC 后保留堆观测，不冒充精确分配计数。软件浏览器和 Node CPU 比较不能证明成熟世界 GPU 帧率。

## 存档与生命周期

故事本体、文案、候选、已读列表均不写入存档，净增长为 0 byte。现有 v11 万象可选块、原物履历和地方沿革仍是唯一保存来源。旧档无 Profile 时安全返回无来源；未知/损坏块沿原 v11 校验拒载，没有放宽规则。

相同世界时刻的重复读取与保存恢复得到同键同内容。来源被上游有界历史淘汰后明确退化，不从当前关系或相似姓名补写。人物转世与夺舍、飞升迁入前的无位面账目、死亡后未保存的 Profile 均不能作为当前人物的已完成行动。只有当前对象的正式身份及开放地图条件通过校验，才提供导航。

UI 仅保留当前检视的一个快照，切换世界/身份即失效；地点卡使用每面板唯一 WeakMap 引用，在 HUD 重建时复用现有快照，不增长对象访问历史。无新增过期队列或永久缓存。
