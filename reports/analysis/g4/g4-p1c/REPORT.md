## 裁断

外海连通掩码可以在真实 `World` 上以可控成本工作；断海不清空已存水，内陆低地可以接收周边水流、蒸发、侵蚀并更新地表类型。依赖显式地形事件失效后，正常水文 tick 不做全图洪泛。建议继续到**独立 opt-in 规则接线与真实 Canvas/Three 验收**，不建议启用默认值或直接合流。

自然生成图的初始封闭低地很少：本轮 128×80 三种子中有 7–10 格低于海平面但不连边界海。这意味着收益主要来自玩家挖渠、筑堤和造湖，不是大幅改变所有创世地图。性能数字没有显示出明确或稳定的单 tick 性能收益；本轮支持的是“功能可行、重建成本可控”，不是加速承诺。

## 原型规则与事件时点

研究模块为 [`oceanHydrologyPrototype.js`](../../../../research/g4-p1c/oceanHydrologyPrototype.js)，身份 `ocean-connected-prototype-v1`，没有接入产品 `hydrologyRules` 或 `Sandbox.update()`。

- 从所有边界上 `height < SEA_LEVEL` 的格子做四邻接洪泛；角落按普通边界格处理。没有低于海平面的边界格时，世界没有静海源；斜角接触本身不连通。
- 掩码和一个队列、一个共享水文 scratch buffer 放在 `WeakMap`；不向 `World` 增加字段，也不序列化。新建或恢复后重建即可。
- 外部地形事件交给 `notifyTerrainMutation()`，带上被改格子的旧高度。只有格子跨越严格的 `< SEA_LEVEL` 通行阈值才失效掩码；水量编辑不触发重建。尺寸或 `height` 数组替换可自动发现。
- 地形事件在**下一个固定 4 日水文 tick 开始时**生效。新连通格归一到静海面；断连格保留原水量，后续参与流动、蒸发、流水侵蚀和热力侵蚀。河道继续使用产品 `maintainRivers()`。
- 沉积遇到静海时作为海洋汇丢弃；封闭低地则参与既有 72% 下游沉积比例。蒸发只在地表水分类阈值变化时登记类型脏格，避免每格每 tick 重算类型。

生成器目前会给所有低于 `SEA_LEVEL` 的格子一次性填水。本原型不在初始化时清空封闭低地的现存水，而让它成为可流动、可蒸发的有限初始水量。三种子 16 tick 后这些低地的合计水量反而增加，来自相邻陆地流入；这不是静海补水。是否要在未来新规则创世时直接干燥封闭低地，仍是应由下一阶段明确的产品规则。

## 定向场景验收

命令：`node scripts/inkbox-g4-p1c-scenarios.mjs`。七组断言全部通过，完整数据在 [`scenarios.json`](evidence/scenarios.json)。场景使用实际 `World`、地形推导、`History`、现有水笔刷、河流基流、存档和地图进度代码。

| 场景 | 结果 |
|---|---|
| 有海、无海、低盆、边角及斜角接触 | 边界低格进入海掩码；无低边界的封闭低盆为干地；仅斜角接触不连通 |
| 开渠入海 | 低于阈值的单格门槛在地形通知后的下一 tick 接海并静海归一 |
| 筑堤断海 | 下一 tick 低盆退出掩码；已有水保留并经普通流动变化，不被清零 |
| 抽水、注水与河流 | 复用 `removeWater()`、`addWater()` 和 `riverBase`，水量改变不误触发掩码重建 |
| 笔刷与撤销 | 用真实 `sculpt()` 和 `History.undo()` 开/关单格水道，两个边界跨越均在下一 tick 更新 |
| 自动侵蚀 | 高程从 `0.3001000` 磨至 `0.2998355`；本 tick 保持旧拓扑，下一 tick 重建并归一 2 格 |
| 蒸发与地形分类 | 低地水深从 `0.0020000` 降到 `0.0005720`，推导类型从浅水更新为干地汀滩 |
| 恢复、地图进度与三界 | 存档不含掩码；恢复后按高程重建相同分类。现有 `expandMap()` 只改开放阶段，不改尺寸或重建掩码。实际生成的上界、幽冥 World 被凡间原型拒绝 |
| 确定性 | 同种子、同输入的两个原型 World 推进 5 tick 后各层 hash 相同 |

自动侵蚀场景第一次用陡峭高侧墙时，热力侵蚀对门槛的回填抵消了流水侵蚀。之后把相邻侧墙调至仍高于海平面、但未触发门槛反向搬运的高程，并保留严格跨阈值断言。它是试验夹具修正，不是产品缺陷，也没有降低断言。

## 自然地图与 V3 对照

使用 `generateWorld()` 的 generation v2、standard、`scatter=false`，V3 与 P1C 从同种子同尺寸的克隆 World 启动，各自推进 16 tick。V3 的所有低海格仍维持静海面；P1C 将不连边界的低地交给动态水文。结果如下：

| 种子（128×80） | 初始连通海格 | 初始断连低格 / 水量 | 16 tick 后仍断连低格 / 水量 | 相对 V3 单格最大水差 |
|---:|---:|---:|---:|---:|
| 173 | 4,551 | 9 / 0.049995 | 9 / 0.072039 | 0.007290 |
| 73,519 | 4,565 | 7 / 0.024630 | 7 / 0.048546 | 0.010111 |
| 912,037 | 4,555 | 10 / 0.060809 | 10 / 0.095275 | 0.006945 |

生成阶段已将这些格子填水，因此本表的初始量是现有生成器留下的一次性水；之后的增长来自周边水流。封闭低地不再被海平面每 tick 拉回，但仍可能接受流入。全量逐格高度、水量、邻居和事件序列保存在机器证据中，例如 seed `73519` 的第一个差异格 `(23,55)`。

## 性能与内存

命令：`node scripts/inkbox-g4-p1c-bench.mjs`。机器为 Windows 10、Node `v24.11.1`、Intel i3-12100。每种尺寸使用 3 种子；V3/P1C 同种子并排生成。每个模型先预热 5 tick，之后每种子采 8 个单 tick，再连续测 16 tick。表中的 tick 单项统计汇总 24 个样本；p95 和最大值用于暴露 JS/GC 抖动。持续段和首次掩码构建各有 3 种子样本，p95 等于三者中的最大值。海门开/闭在三个种子、三个尺寸共 9 组重复。计时是 Node CPU 计时，不是 GPU 或浏览器性能结论。

| 尺寸 | V3 单 tick 中位 / p95 ms | P1C 单 tick 中位 / p95 ms | P1C 首次洪泛中位 / 最坏 ms | 16 tick V3 中位 / 最坏 ms | 16 tick P1C 中位 / 最坏 ms | P1C 掩码+队列+scratch |
|---|---:|---:|---:|---:|---:|---:|
| 200×128 | 0.590 / 1.145 | 0.647 / 1.488 | 0.226 / 0.833 | 10.542 / 10.687 | 11.601 / 13.938 | 230,400 B |
| 288×180 | 0.930 / 1.375 | 0.658 / 0.812 | 0.234 / 0.274 | 15.082 / 20.061 | 10.504 / 11.760 | 466,560 B |
| 512×320 | 2.377 / 3.490 | 2.065 / 2.517 | 0.636 / 0.985 | 39.643 / 41.235 | 33.685 / 35.393 | 1,474,560 B |

这不是速度提升结论：V3 与 P1C 在模拟不同水文状态，计时也受 Node JIT、垃圾回收和机器负载影响。它表明本次样本下 tick 成本在相近量级；掩码不是每 tick 重算。16 tick 样本中 200×128 三种子共发生 2 次阈值穿越重建，其余尺寸样本为 0 次。单格门槛事件的独立洪泛时间最大为：开渠 0.749 ms、筑堤 0.617 ms；含该 tick 其他水文工作的墙钟最大分别为 3.933 ms 和 3.773 ms。

P1C 缓存是每格 9 字节：1-byte mask、4-byte BFS 队列和复用的 4-byte 浮点 scratch。512×320 为 1.406 MiB。V3 懒分配的 scratch 在 200×128 与 288×180 样本中为 12 bytes/cell，在 512×320 样本中为 8 bytes/cell（1,310,720 B）；差异来自热力缓冲是否被分配。这不是全堆内存测量，不计 JS 对象、类型脏表或渲染缓存。大图中 P1C 相对该观测多约 160 KiB。

## 规则可理解性和限制

- 玩家把单格门槛挖到 `height < 0.3`，整条正交相连的低水道在下一水文 tick 成为静海；水面不是沿河口逐格传播。反向筑堤到 `height >= 0.3` 后，水道断开，既有水保留。
- 四邻接容易解释、计算稳定，但纯斜角接触不通。单格宽水道也足以接海，没有宽度、潮汐、流量或连通稳定时间；这会显得机械，需在正式 Canvas/Three 场景和玩家路径上评估。
- 当前地形更新通知是研究适配器 API。漏掉任何 height 修改事件会产生过期掩码。若每 tick 用全图高程快照来兜底，虽避免洪泛，也会新增每 tick O(N) 扫描与复制；不建议这样集成。
- 水量变化必须在类型阈值跨越时刷新 `type/qi`。原型明确覆盖蒸发由湿转干的边界；正式接线还要覆盖密集流动、笔刷撤销、V3 存档恢复和 Three 几何更新。
- 本轮未在浏览器中运行 P1C，因为规则没有接入 Canvas/Three 产品循环。R2 浏览器 PASS 是旧基线证据，不代表本原型已经通过实际 UI 验收。

## 正式接线触点与下一最小范围

1. 在 `hydrologyRules.js` 增加独立规则身份（建议生产名 `ocean-connected-v3`），显式分流，不改 `legacy-v1`、P1A Oracle 或 `static-sea-v2`；在 `worldCreation.js`/恢复后初始化缓存，并决定生成器一次性填入的封闭低地水是否保留为有限初始量。
2. 为 `powers.js` 的 sculpt/flatten/roughen、`History.undo()`、`render3d/terrain/sculpt.js` 的 Three 路径，以及 `hydrology.js`/新规则的流水和热侵蚀，接统一的海平面跨阈值事件。真实尺寸扩展应随新 `World`/数组自动重建；现有 `mapProgress.expandMap()` 只改访问阶段，不需触发。
3. 存档只保存规则身份和原有地形/水层，不保存掩码。恢复后根据高程重建；只有增加新的持久数据时才重新评估 `SAVE_VERSION`。
4. 接线后必须做一轮 Canvas 与 Three 的真实浏览器验收：创世、挖渠、筑堤、Undo、自动侵蚀、保存/读取、Three 场景重绑与上界/幽冥隔离。该工作属于独立 P1C 工程阶段；不自动启用默认规则。

本分支只新增研究原型、脚本、证据和报告；没有改 `src/inkbox`、`main`、SAVE_VERSION、冻结 P1A Oracle 或发布包，没有创建 PR，也没有合并。
